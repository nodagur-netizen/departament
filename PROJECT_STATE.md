# Project state

## Контрольная точка — 2026-07-26

Это текущая каноническая точка продолжения проекта. Основа локальной среды и конфигурации зафиксирована коммитом `e418133`; production-фронтенд после него **ещё не переработан**: маршрут `/` остаётся прежней «Панелью кафедры».

### Сделано

- Созданы три статических визуальных концепта. Владелец выбрал `01 — «Лабораторный журнал»` как единственное каноническое визуальное направление: `frontend/concepts/01-lab-notebook.html` (локально: `http://localhost:18180/concepts/01-lab-notebook.html`).
- Это статическая демонстрация с синтетическими данными и без API; она не является production-экраном и её действия ничего не изменяют.
- Нормативная дизайн-система — `DESIGN.md` и `.impeccable/design.json`. Все новые или мигрируемые экраны должны следовать им, а не извлекать правила заново из прототипа.
- Технологический контур остаётся прежним: Go + vanilla HTML/CSS/JS, same-origin.

### Не сделано и обязательные границы

- Выбранный концепт не перенесён в реальный frontend, поэтому визуально `/` пока не менялся.
- До production нельзя считать API безопасным: требуется закрыть разрыв auth middleware / public DTO и остальные Phase 0 security/data hardening gates.
- Доступ остаётся по default deny: заявки рассматривают `admin` и `lab_head`; после входа `guest` и `student` видят только свой профиль и публичные карточки оборудования.

### Следующее решение и следующий шаг

Следующий шаг — ограниченная фаза миграции реального frontend shell и базовых компонентов по `DESIGN.md`, без расширения доменного scope. Реальные API подключать и сохранять их контракты только после security hardening (auth/RBAC, отдельный публичный DTO и связанные проверки) из Phase 0.

### Как начать следующую сессию

1. Прочитать по порядку: `PRODUCT.md`, этот файл, `DESIGN.md`, `docs/ARCHITECTURE.md`, `docs/MVP.md`, `docs/DESIGN_SYSTEM_PLAN.md`, `docs/IDENTITY_AND_ACCESS.md`; затем открыть выбранный концепт.
2. Перед изменениями проверить `git status --short` и `git diff --check`; не перезаписывать существующие несвязанные правки.
3. Для локального запуска выполнить `./scripts/dev.ps1`, затем проверить `http://localhost:18180/` и выбранный концепт. Скрипт сам выставляет `REG_CONFIG_NAME=local`; не фиксировать и не пытаться восстановить временный PID процесса — при следующем запуске использовать новый процесс.
4. Для проверки кода выполнить `./scripts/check.ps1`. Не использовать production-данные или секреты.

## Текущий этап

Основа локальной среды и планирования завершена; выбран визуальный курс. Следующая реализация — ограниченная миграция интерфейса после необходимого security/data hardening, а не новый поиск визуального направления.

## Зафиксированные решения

- Backend: Go modular monolith, Gin и sqlx.
- Frontend: same-origin embedded vanilla HTML/CSS/JS с переходом на native ES modules.
- MVP data store: SQLite только для одного инстанса; PostgreSQL при multi-instance/HA/материальной конкурентной записи.
- Целевая auth-модель: server-side opaque sessions в `HttpOnly`/`Secure`/`SameSite` cookie, CSRF/Origin checks, rate limits и централизованный RBAC.
- Миграции: embedded, versioned, ledger/checksum. Аудит: append-only.
- Не создавать преждевременную универсальную таблицу инвентаря.
- До закрытия Phase 0 запрещены реальный deployment и ПДн.
- Подтверждено: нужны роли; примеры — студент, заведующий лабораторией и гость. Любой может открыть публичную карточку оборудования и подать заявку на регистрацию как студент или гость.
- Принятое обратимое безопасное решение: affiliation отделён от role/permission; саморегистрация создаёт `pending`-заявку, а после ручной проверки — аккаунт с временным паролем и обязательной сменой. Роли MVP: гость, студент, сотрудник, заведующий лабораторией, администратор; default deny.
- Публичная карточка доступна только по непрозрачному `public_id`, через отдельный DTO, без каталога и внутренних данных. Полный контракт: [docs/IDENTITY_AND_ACCESS.md](docs/IDENTITY_AND_ACCESS.md).
- Заявки на регистрацию рассматривают владелец-администратор и заведующий лабораторией; одобрение и отклонение аудируются. `student` и `guest` после входа пока видят только публичные карточки оборудования и собственный профиль.
- Разработка пока на текущей машине; production позже будет выбран между VPS и сервером организации.
