# Идентификация и доступ

Этот документ — единый контракт для будущей реализации identity, RBAC и публичной карточки оборудования. Он не содержит персональных данных, учётных данных или секретов.

## Статус решений

### Подтверждено владельцем

- Роли необходимы; названы примеры: студент, заведующий лабораторией и гость.
- Любой посетитель может открыть публичную страницу отдельного оборудования.
- Любой может подать заявку на регистрацию как студент или гость.
- Разработка пока идёт на текущей машине. Production позже будет размещён либо на VPS, либо на сервере организации.

### Принятый обратимый безопасный default

- `affiliation` (принадлежность к кафедре) отделена от `role` и `permission`.
- Заявка на регистрацию — отдельная сущность, не аккаунт. Саморегистрация создаёт только `pending`-заявку без активного аккаунта, логина или пароля.
- После ручного одобрения создаются логин, временный пароль и флаг `must_change_password`; временный пароль передаётся пользователю вне журналов и не хранится в открытом виде.
- Авторизация реализуется как `role → permission`; при отсутствии явного разрешения доступ запрещён (`default deny`).
- Стартовые роли MVP: `guest`, `student`, `staff`, `lab_head`, `admin`. Они могут быть уточнены до реализации без миграции продуктового смысла.
- Публична только отдельная карточка оборудования по непрозрачному `public_id`; публичного каталога, поиска и перечисления объектов нет.
- Заявки рассматривают `admin` (владелец) и `lab_head`; решения `approved` и `rejected` всегда создают audit event.
- После входа `guest` и `student` пока имеют только публичные карточки оборудования и собственный профиль.

### Открыто

- Конечные полномочия `staff` и `lab_head` для каждого доменного модуля.
- Production-место, сеть, домен, TLS-терминация и процедура выдачи временного пароля.

## Модель сущностей и состояний

| Сущность | Назначение | Состояния / правила |
| --- | --- | --- |
| `person_profile` | Минимальный профиль человека, независимый от доступа | Может существовать без аккаунта; хранит только согласованный минимум данных. |
| `affiliation` | Связь профиля с кафедрой: `student`, `teacher`, `staff`, при необходимости даты и подтверждение | Не выдаёт прав доступа. У одного профиля возможны несколько affiliation. |
| `account` | Учётная запись для входа | `active`, `disabled`; связана с одним профилем; содержит логин, хэш пароля и `must_change_password`. |
| `role_assignment` | Назначение роли аккаунту | Роли назначаются явно; одна учётная запись может иметь несколько ролей. |
| `permission` | Именованное действие над ресурсом | Проверяется на сервере в middleware и service-слое; отсутствие разрешения — отказ. |
| `registration_request` | Заявка публичного посетителя на получение доступа | `pending` → `approved` / `rejected` / `withdrawn`; одобрение создаёт аккаунт отдельной транзакцией и аудируется. |

`person_profile` не равен `account`: человек может подать заявку, не имея доступа; отключённый аккаунт не удаляет историю операций и affiliation. Роли описывают полномочия, а не должность или учебный статус.

## Миграция текущих категорий

| Исходная категория | Целевая affiliation | Стартовая роль | Примечание |
| --- | --- | --- | --- |
| Студент | `student` | `student` после одобрения | Affiliation не открывает внутренние данные сама по себе. |
| Преподаватель | `teacher` | `staff` только при необходимости рабочих прав | Преподаватель не получает роль автоматически. |
| Сотрудник | `staff` | `staff` после явного назначения | Для людей с несколькими статусами допускаются несколько affiliation. |
| Заведующий лабораторией | `staff` или `teacher` по фактической связи | `lab_head` | Это роль с полномочиями, а не отдельная affiliation. |
| Внешний гость | нет affiliation, если связь не подтверждена | `guest` после одобрения | Не путать публичного анонимного посетителя и вошедшего гостя. |

До миграции существующие записи должны быть отображены в черновой таблице соответствий и вручную подтверждены владельцем. Автоматически назначать повышенные роли запрещено.

## Стартовая матрица разрешений MVP

Матрица ниже — обратимый безопасный default, а не подтверждённый окончательный регламент. `✓` означает разрешение; `—` — явное отсутствие разрешения. Все неуказанные разрешения запрещены.

| Permission / ресурс | Анонимный посетитель | `guest` | `student` | `staff` | `lab_head` | `admin` |
| --- | --- | --- | --- | --- | --- | --- |
| `public_equipment.read` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `registration_request.create` | ✓ | — | — | — | — | — |
| `account.read_self`, `account.update_self`, смена своего пароля | — | ✓ | ✓ | ✓ | ✓ | ✓ |
| `equipment.read_internal` | — | — | — | ✓ | ✓ | ✓ |
| `equipment.create`, `equipment.update` | — | — | — | — | ✓ | ✓ |
| `keys.read`, `keys.transaction` | — | — | — | ✓ | ✓ | ✓ |
| `accounts.manage`, `roles.assign`, `audit.read` | — | — | — | — | — | ✓ |
| `registration_request.review` | — | — | — | — | ✓ | ✓ |

Будущие модули (мебель, химикаты, посуда, статьи, ассистенты) не получают разрешения по умолчанию: их матрицы добавляются вместе с доменным решением.

## Поток регистрации и первого входа

```text
Публичный посетитель
  → отправляет заявку (student | guest)
  → registration_request: pending
  → ручная проверка владельцем-администратором или заведующим лабораторией
  → approved + создаётся account(active, must_change_password=true)
  → пользователь получает логин и временный пароль безопасным согласованным способом
  → первый вход
  → обязательная смена пароля
  → обычная сессия и доступ по permissions
```

- Публичная форма принимает минимальный согласованный набор данных, имеет rate limit и возвращает нейтральный ответ, не раскрывая факт существования профиля или аккаунта.
- `approved`, `rejected`, выдача/сброс временного пароля и назначение ролей создают audit event. Пароли, хэши, cookie, токены и полный текст чувствительных полей заявки в аудит не попадают.
- Повторная заявка и конфликт с существующим аккаунтом обрабатываются внутренней проверкой; публичный ответ остаётся нейтральным.
- Отклонение, отзыв или деактивация не удаляют обязательный аудит. Удаление персональных данных определяется отдельной политикой retention.

## Публичная карточка оборудования

### Route policy

| Маршрут | Доступ | Политика |
| --- | --- | --- |
| `GET /public/equipment/{public_id}` | Публичный | Только единичная карточка по opaque `public_id`; `X-Robots-Tag: noindex, nofollow`; без индекса, списка, поиска и browse-навигации. |
| `GET /api/v1/equipment/*` и внутренние страницы | Только авторизованный actor с permission | Внутренние DTO и данные не используются для публичного ответа. |
| `POST /registration-requests` | Публичный | Только создание заявки; rate limit, CSRF/origin-политика по выбранному механизму формы, нейтральный ответ. |
| `POST/PATCH/DELETE /api/v1/*` | Только авторизованный actor с permission | Server-side session, CSRF и `Origin`/`Referer` checks; аудит изменяющих операций. |

Публичный URL может быть закодирован в QR только после реализации этой отдельной карточки. QR генерируется same-origin и не передаёт адрес внешнему сервису.

### `PublicEquipmentDTO`

Публичный handler формирует отдельный allowlist DTO. Допустимый минимум для MVP: `public_id`, безопасное публичное название, категория/тип, публичный статус доступности и дата последнего обновления при необходимости. Состав полей утверждается при проектировании карточки; всё остальное закрыто.

Никогда не выдаются: внутренний ID, инвентарный номер, точная локация, ответственный, внутренние документы, история, аудит, серийный номер, данные обслуживания, привязки к ключам, контакты и любые неутверждённые метаданные. Внутренний `EquipmentDTO` не должен сериализоваться в публичном route.

## Проверки реализации

- Для каждого route есть тесты anonymous/unauthenticated/authenticated и проверка permission boundary.
- Тесты подтверждают, что запросы к закрытым API не обходят RBAC прямым HTTP-вызовом.
- Тесты публичной карточки подтверждают отсутствие запрещённых полей и невозможность перечисления объектов.
- Тесты регистрации подтверждают, что заявка не даёт активного аккаунта, а первый вход требует сменить временный пароль.
- Все изменения ролей, статуса заявки и аккаунта имеют аудит без секретов и лишних персональных данных.
